# 登山赛车（Hill Climb Racing）

**🎮 在线试玩（网页版）：<https://3844775306-code.github.io/HillClimb/>** ｜ 📦 仓库：<https://github.com/3844775306-code/HillClimb>

用 Godot 4.7 做的 2D 物理越野小车游戏。所有画面都是代码程序化绘制的，**没有任何美术资源**
（`_draw()` + `draw_polygon` / `draw_circle` / `draw_string`），车辆是真实的 2D 刚体物理。

## 运行

```bash
"D:/Downloads/Godot_v4.7.2-stable_win64.exe/Godot_v4.7.2-stable_win64.exe" --path .
```

或用 Godot 编辑器打开本目录，直接 F5 运行 `scenes/main.tscn`。

## 操作

开车时：

| 按键 | 动作 |
| --- | --- |
| `→` / `D` / 手柄 RT | 前进 |
| `←` / `A` / 手柄 LT | 倒车 |
| `空格` / 手柄 B | 开 / 关车灯（**只有黑夜图有车灯**，见「车灯」） |
| `R` / 鼠标点击 / 触屏点击 | 重新开始（结算面板上） |
| `V` / 手柄 X | 换车（结算面板上） |
| `M` | 换地图（结算面板上） |
| `G` / 手柄 Y | 回车库改装（结算面板上） |

选车界面（**启动第一站**）：

| 按键 | 动作 |
| --- | --- |
| `←` `→` / `A` `D` / 手柄十字键 | 选车 |
| `回车` / 空格 / 手柄 A | 就要这辆，进车库 |
| `Esc` / 手柄 B | 不挑了，直接开存档里那辆进车库 |
| 鼠标 / 触屏 | 直接点卡片 |

车库里：

| 按键 | 动作 |
| --- | --- |
| `↑` `↓` / `W` `S` / 手柄十字键 | 选改装项 |
| `→` / `D` / 空格 / 手柄 A | 买一级 |
| `V` / 手柄 X | 换车（回选车界面） |
| `回车` / 手柄 Start | 去选地图 |
| 鼠标 / 触屏 | 直接点某一行的价格药丸就能买，点按钮往下走 |

流程是 **选车 → 车库 → 选图 → 开跑**，主循环就是「挑一辆车、给它攒钱改装、开跑」。

**选车为什么排在车库前面**：升级是**按车分开**的（见下节），车库那一页的四个数字属于
当时那辆车，所以得先把车定下来才有得升。车库页眉和选车卡片上都写着当前是哪辆。

结算面板上按 `G` 回车库、`V` 换车、`M` 换图，按 `R` 或点一下就直接再跑一局
（车、地图、改装全部沿用上一局）。

## 玩法

- **里程**：向右开得越远分数越高（10 px = 1 m）。
- **燃油**：一直消耗，油门踩满耗得更快。路上捡油桶补充，**没油就结束**。
- **金币**：散落在路上，捡到计数。
- **翻车**：车顶的 `Area2D` 碰到地面就算摔了（后空翻、倒扣都会触发）。

地形无限向右延伸，坡度随距离越来越陡（振幅从 42 px 涨到上限 140 px）。

### 存档

存档写在 `user://save.cfg`（Windows 下在
`%APPDATA%/Godot/app_userdata/HillClimbRacing/`），存两样东西：

- **最远记录**：翻车结算时用 `SaveData.submit_distance()` 更新，只在破纪录时写盘。
- **金币总数**：每捡一枚就立刻 `SaveData.add_coins(1)` 入账。**不等翻车结算**——
  这样半路 Alt+F4 或者直接关窗口也不会把这一局捡的金币丢掉。

顶栏四列是「里程 / 金币 / 最远记录 / 金币总数」。当前这局超过历史记录时，
「最远记录」那一列会**当场**变金色跳成新数值，不用等翻车。

`SaveData` 在 `project.godot` 里注册成 autoload（`*res://scripts/save_data.gd`），
随时全局可访问。它有一个 `persist` 开关：**跑自动测试的用例必须设
`SaveData.persist = false`**，否则自动机会开出上千公里，一跑就把玩家真正的存档
覆盖成垃圾数据（`tests/save.gd` 还会真的删写文件，所以它自己会先备份再还原）。

### 解锁（地图和车都要买）

开局只给四张图和两辆车，其余的花金币买：

| | 白送 | 解锁价 |
| --- | --- | --- |
| 地图 | **前 4 张**：平原 / 荒漠 / 雪地 / 火山 | 每张 **50000** |
| 车 | **前 2 辆**：越野车 / 摩托 | 每辆 **100000** |

价格和名单在 `scripts/maps.gd` 的 `FREE_COUNT` / `UNLOCK_PRICE`、`scripts/vehicles.gd`
的同名常量里，**不在 `save_data.gd`** —— 那边只管收钱（`SaveData.unlock_map()` /
`unlock_vehicle()`），「这张图值多少」是地图表自己的事。写法是「`IDS` 的**前几个**」
而不是一张免费名单：名单得跟 `IDS` 手工同步，加一张新图两处就会漂。

#### 买法是两下，不是一下

点一张没选中的卡**只是把光标挪过去**，再点一下（点同一张）才真扣钱。一次点中就买的话，
翻页的时候手指擦过一张 50000 的图，钱就没了。买下来之后**也不顺手进图**：卡片当场
变成通的样子、金币当场少掉，玩家看得见自己买到了什么，再按一下才出发。

买不起的话那一下什么也不发生：价钱那行转成暗红（`HillLockBadge.DENIED`），底下那行
提示换成「金币不够」—— 提示一共三句（`点一下选中` / `再点一下购买` / `金币不够`），
钱不够的时候**不能**说「再点一下购买」，那是句假话，点了什么都不会发生。

#### 免费的那几张**不写进存档**

`[unlocked]` 段里只有**花钱买的**。判「能不能开」只走 `SaveData.map_unlocked()` /
`vehicle_unlocked()`（它们内部 `Maps.is_free()` or `bought_*`），**不要直接查
`bought_maps`** —— 免费图根本不在那个字典里，查了会把平原判成锁着的。

顺带，`Maps.is_free()` / `Vehicles.is_free()` 对**不认识的 id 一律返回 false**：
这两句被当成权限判断用，权限判断的兜底必须是否决。

#### 加了这套东西之后的老存档：玩过的就算已解锁

和玩家确认过的迁移规则（`SaveData._grandfather()`，只在装档时跑、只改内存）：

- **地图**：有纪录（`best > 0`）就白送。玩家在上面跑出过成绩，把成绩锁在 50000 后面
  说不过去。
- **车**：任何一项升级花过钱（等级 > 0），或者它**正是存档里选中那辆**，就白送。
  选中那辆单列，是因为「选中但还没改装就退出了」是可能的，而**选中的那辆就是玩家
  正在开的那辆**，收回去等于把他手上的车抢走。

这条是幂等的，所以不需要判「档里有没有 `[unlocked]` 段」：全新档三项条件一个都不满足，
跑一遍是空操作；而判段存在与否反而要区分「老档」和「买了第一张图之后的新档」两种情形，
多一处会漂的判据。

⚠ **后果：在这套东西之前就已经玩过的存档，12 张图 8 辆车会全部被认领成已解锁**，
一进选图页看到的是「全通」。游戏里**没有清档的入口**（`SaveData.reset_progress()`
只有测试在调），想在界面上看购买流程，得手动删掉 `user://save.cfg`（Windows 下是
`%APPDATA%/Godot/app_userdata/HillClimbRacing/save.cfg`）—— 删之前先把上面一行的
路径对着自己的机器核一遍，那是唯一一份进度。

`SaveData._repair_locked_selection()` 是装档时的兜底：选中的图/车要是锁着的（手改过
cfg、以后删掉某张图），换回平原 / 越野车。它有存在的必要 —— 存档里 `selected_map`
和 `selected_vehicle` 就是两个键，玩家按「继续」会直接开进那张图。

**`select_map()` / `select_vehicle()` 本身不加闸。** 它们是底层 setter，测试正是靠它们
摆出「开坦克跑 30 秒」这种场景；闸放在界面那一层（选图 / 选车两页的点击处理），坏档
由上一条修复兜住。

#### 锁卡长什么样

选图 / 选车两页上锁着的卡片：整张压暗，正中间一个挂锁，下面一块深色底板写着价钱，
再下面一行是提示。**卡片本身照常画完**（预览、名字、参数、推重比），玩家得能看见
自己买的是什么东西。两页共用一份实现 `scripts/lock_badge.gd`，因为那两页的卡片几何
本来就是同一套（卡宽都锁死在 276.5）。

锁和底板的位置是**量出来的，不是摆好看的**：

- 挂锁画在 `LOCK_CY = 48`，整个落在卡片顶部那条 118 px 的预览带里 —— 那一带里
  一个字都没有。**不能往卡片中段挪**：挂锁横向是 `cx ± 27`，压到名字或参数行上
  就会盖掉字。
- 底板占 172..238。`tests/mapselect` 和 `tests/vehicleselect` 都拿真字体量出每一行
  文字的**墨迹**范围（不是 `get_ascent()` 那个行盒），断言每一行要么整个在底板里、
  要么整个在外面，**不许被从当中切开**。

### 改装（升级）

在车库里用攒下的金币给车升级。四项，**各 10 级**，花销 **80 / 92 / 106 / 122 / 140 /
161 / 185 / 213 / 245 / 282**（每级 ×1.15），单项点满 1626 币，四项全满 6504 币。

| 项 | 满级倍率 | 作用 |
| --- | --- | --- |
| 引擎 | ×1.216 | 扭矩。爬坡更有劲，翘头风险上升 |
| 极速 | ×1.263 | 齿比。跑得更快，静止推力不变 |
| 油箱 | ×1.600 | 容量。一箱油烧得更久 |
| 敏捷 | ×2.000 | 转动惯量 ×0.5。更利索，但颠簸路面更跳 |

**改装数据集中在 `scripts/upgrades.gd`**（纯粹的静态表 + 倍率函数，不依赖节点），
存档、车库界面、车辆三边都引用它，改数值只需要动这一个文件。

#### 升级是按车分开的

**每辆车各有一套等级**，金币是共用的。给巴士点满油箱，摩托的油箱还是 0；换车之后
要重新练。和「里程纪录不按车分」正好相反，理由也正好相反：

- 纪录是「这张图你跑过最远的一次」，按车分等于惩罚玩家换车；
- 升级是「你给这台车投了多少钱」。四辆车的基数差着好几倍（巴士 701、摩托 900、
  赛车 1254），同一套等级在不同车上根本不是同一个意思 —— 共享的话练满一辆车等于
  白送另外三辆，换车就成了「带着神装换个壳」。

存档里每辆车一份，键名是 `<车id>/<项id>`（`[upgrades]` 段里 `racer/engine=7`）。
加多车之前的平表老档（`engine=3`）会自动挂到**默认那辆越野车**名下，见
`SaveData.legacy_level()` —— 那条兼容路径只会走一次，新格式写盘时老键就消失了。

#### 10 级不是把每级倍率照抄一遍

从 4 级改成 10 级时，四个每级倍率是**照「满级落在哪儿」反推**的，让 Lv.10 正好等于
旧版的 Lv.4，所以**满级强度分毫未变**，只是把同一段涨幅切成了十份。照抄会坏两处：

- **敏捷**旧值 −12.5%/级，十级是 `1 − 1.25 = −0.25` —— 转动惯量成了**负数**，刚体
  直接不成立（第 8 级就归零了）；
- **引擎**旧值 ×1.05/级，十级是 ×1.629，越野车满级推重比 1.68 × 1.629 = 2.74，远超
  1.45 的翘头线 —— 就是下一节拼命避免的那种「练满即练废」。

`tests/upgrade_calib.tscn` 的 A 段把这两条钉住了：四条「满级 = 旧版 Lv.4」的等式，
外加「每一项 11 个等级逐级更好、显示倍率不掉到 1 以下」。花销曲线的基价是 80，
但增长率必须从 ×1.5 降到 ×1.15 —— 十级还按 ×1.5 涨，最后一级单独要 3075 币。

#### 为什么极速要做成「齿比」而不是「更大的推力」

这是这个系统里唯一一处非做不可的设计。静止推力（推重比）是：

```
两轮推力 = 2 × 轮目标转速 × 扭矩系数 ÷ 轮半径
推重比   = 两轮推力 ÷ 整车重量
```

如果引擎和极速**都**直接加推力，两项全满就是 1.216 × 1.262 = 1.53 倍推重比 ——
超过约 1.45 的翘头线，玩家花 1300 币把自己变成一台必翻的车。

所以极速改的是齿比：`max_wheel_speed ×= k` 同时 `motor_strength ÷= k`，静止推力
**分毫不变**，而轮子转得更快。于是：

- **推重比只由引擎一项决定**，满级 1.222，离 1.45 还有余量。
- 极速不但不伤爬坡，反而**帮**爬坡 —— 实测 40° 稳态爬坡里极速满级和引擎满级
  一样快（都是 +32%），因为爬坡时轮子被压低转速、正好落在扭矩曲线的中段。

车库页脚会实时显示当前推重比和翘头线，快贴线了就变金色、到了变红色。

#### 实测（`tests/upgrade_calib.tscn`）

> ⚠ 下面这些数字量于 `max_wheel_speed = 30`，车辆后来被调到 100，**除了 E1 的烧干
> 用时以外都已过期**。见「调参」一节的过期提示。

推重比（A 段，纯计算）：

| 配置 | 推重比 |
| --- | --- |
| 原厂 | 1.005 |
| 引擎 Lv2 | 1.108 |
| 引擎 Lv4 | **1.222** |
| 翘头线 | 1.45 |

平路起步 3 秒全油门（B 段）——**所有配置的最大抬头都是 0.0°、前轮离地 0.00s**：

| 配置 | 末速 |
| --- | --- |
| 原厂 | 510 px/s |
| 引擎 Lv4 | 529 px/s |
| 极速 Lv4 | 607 px/s |
| 引擎 Lv4 + 极速 Lv4 | 638 px/s |

40° 稳态爬坡（C 段）—— 爬坡只看引擎和齿比，跟推重比完全对得上：

| 配置 | 坡面均速 | 相对原厂 |
| --- | --- | --- |
| 原厂 | 206 px/s | — |
| 引擎 Lv4 | 272 px/s | +32% |
| 极速 Lv4 | 270 px/s | +32% |
| 引擎 Lv4 + 极速 Lv4 | 331 px/s | +61% |

**极速 Lv4 和引擎 Lv4 的爬坡速度一样**，这正是齿比设计的直接证据：极速不碰推重比，
它对爬坡的帮助全部来自「轮子被压低转速时扭矩更高」，和引擎加扭矩是同一件事的两个方向。
两项一起上则是 +61%，接近相乘。

平地精确烧干用时（E1 段）—— 油耗只跟油门有关（怠速 1.6 + 全油门 4.4 = 6.0/s），
所以用时严格等于容量 ÷ 油耗率，这是唯一能精确验证油箱倍率的场合：

| 配置 | 容量 | 实测烧干用时 | 容量 ÷ 油耗率 |
| --- | --- | --- | --- |
| 油箱 Lv0 | 100 | 16.70s | 16.67s |
| 油箱 Lv4 | 160 | 26.70s | 26.67s |

容量比 1.600，用时比 **1.599**。B/C/E1 三段跨 5 次运行**逐位相同**（E1 每次都是
16.70s / 26.70s / 8255 px / 13395 px）。

#### 实现上的两个关键点

- **Lv.0 必须是恒等变换。** `Upgrades.apply()` 是把倍率**乘在车的当前值上**，
  不是拿常量重算一遍。这样编辑器里手调的 `@export` 值、测试里临时设的值都能
  留下来，而且「升到 0 级」就是原厂车 —— 测试只要 `SaveData.reset_progress()`
  就能拿到一台干净的原厂车，不需要额外的开关。
- **买升级要一次写盘。** `SaveData.buy_upgrade()` 在内存里把等级和金币一起改完，
  最后只 `save_data()` 一次。要是拆成「先扣钱存盘、再升级存盘」，中间崩掉就会
  留下钱扣了、等级没给的坏档。
- **`Upgrades.apply()` 必须在 `fuel = fuel_max` 之前**（`car.gd` 的 `_ready()`）：
  升级会改 `fuel_max`，先加满再改等于白升。
- 老存档没有 `[upgrades]` 段，`ConfigFile.get_value` 会给回默认值 0，等于原厂车，
  不需要写迁移代码。

## 调参

> **⚠ 本节和下面「改装」节里的实测数字目前全部过期。**
>
> 那些数字都是在 `max_wheel_speed = 30` 时量的（爬坡、续航、惯量对比、改装标定）。
> 2026-10-01 车辆被重新调过：`max_wheel_speed` 从 30 改到 **100**（`motor_strength`
> 仍是 60000，于是推重比从 1.005 涨到 **3.351**，远超 1.45 翘头线）。
> 车速变了 3.3 倍，所有跟速度有关的量都会变，**在重新量之前别拿下面的数字做依据**。
>
> 不受影响、仍然有效的部分：改装的花销曲线与倍率表、油箱烧干用时（油耗只跟油门有关，
> 与车速无关）、代码结构、以及所有测试上的坑。
>
> 判断一份数字还作不作数的办法：看它是不是依赖车速。`tests/upgrade_calib.tscn` 的
> A 段会直接打印当前的原厂推重比，并在这条线被越过时给出警告。

改 `scripts/car.gd` 顶部的 `@export` 分组，编辑器里选中 Car 节点也能实时调：

- `max_wheel_speed`（默认 30）—— 轮子目标转速，决定极速
- `motor_strength`（默认 60000）—— 扭矩系数，**决定爬坡能力**
- `max_torque`（默认 2000000）—— 只做极端情况兜底，正常行驶不会触及
- `fuel_max` / `fuel_idle_drain` / `fuel_throttle_drain` —— 一箱油能跑多久
- `inertia_scale`（默认 2.0）—— 三个刚体的**转动**惯量倍率，见下

**调爬坡能力时看推力自重比**，别看扭矩绝对值。静止时：

```
单轮推力 = max_wheel_speed × motor_strength ÷ 轮半径
两轮合计 ÷ 整车重量(174) = 推力自重比
```

自重比 < 1 就爬不上 45° 以上的坡（坡度 θ 需要 sin θ 倍自重）。**现值不要去记，
让代码算**：`Upgrades.stock_thrust_ratio()` 直接从 `scenes/car.tscn` 读出来算，
车库页脚也显示同一个数。改完可以用 `tests/climb.tscn` 直接量极限坡度。

关于「多少倍会翻车」这条线，有个反直觉的实测结论（`tests/upgrade_calib.tscn` 的 B 段）：
**平路上把推重比堆到 3.35 也不会翘头**，最大抬头 0.0°、前轮一秒都不离地 —— 因为 2D 的
`PinJoint2D` 不传递扭矩，马达的反作用力矩根本传不到车身上，平路起步没有让车后仰的力矩。
**所以拿平路起步测不出翘头风险**，这一项的 0.0° 不能当成「安全」的证据。

真实地形的鼓包才会把车掀翻：推重比 3.35 那台车 20 秒里翻车四次、只跑出 288 m，
而 1.005 那台一次都不翻、跑出 792 m。**但要注意这两组是两台不同的车**（转速 100 对 30，
车速也差 3.3 倍），「翻车是因为推力太大」还是「因为车速太快被鼓包弹飞」目前**没有分离
测量**，别把这两条数字当成翘头线设在 1.45 的证据。

### 惯性（`inertia_scale`）

「车太飘、碾过碎石就弹起来」调这个。**注意调的是转动惯量，不是质量**：

- **把质量整体放大 k 倍、同时把力矩也放大 k 倍，运动方程两边同乘 k，加速度分毫不变**
  —— 纯质量缩放是个恒等式，玩家感觉不到任何差别。
- 只加质量不加力矩则会直接压低推重比，把好不容易调出来的爬坡能力毁掉（见上面
  「调爬坡能力时看推力自重比」）。
- 转动惯量没这个问题：它只改变**转动**的难易，不碰推重比，所以爬坡只受「轮子
  提速变慢」这一个间接影响。

实测（`tests/inertia.tscn`；⚠ 量于 `max_wheel_speed = 30`，已过期，见「调参」）：

| 倍率 | 搓板路出速 | 俯仰标准差 | 40° 稳态爬坡 | 45° 稳态爬坡 |
| --- | --- | --- | --- | --- |
| 1.0 | 254 | 2.53° | 237 px/s | 193 px/s |
| 2.0 ← 默认 | 348 | 2.50° | 212 px/s | 190 px/s |
| 4.0 | 329 | 2.15° | 193 px/s | 165 px/s |

2.0 是收益/代价的拐点：搓板路提速明显，爬坡只掉 11%（40° 上仍有 212 px/s，
远没到爬不动的程度）。4.0 开始伤爬坡。想要极限爬坡就调回 1.0。

真实地形上（`tests/range.tscn`，同种子 1337）：1790.0 m → 1588.1 m，**−11%**，
跟 40° 稳态爬坡的 −11% 对得上，可信。两者的最长卡住时长都是 0.5 s —— 没有因为
调惯量而重新引入搁浅 bug。

一个反直觉的点：**单个车壳的惯量对俯仰几乎没影响，真正起作用的是轮子的惯量**。
试过只放大车壳（`tests/inertia.tscn` 的 `"chassis"` 模式），搓板路各项指标纹丝不动
（2.53 → 2.79 → 2.44，全在噪声里）。所以这个倍率是三个刚体一起乘的，别只调车壳。

实现上踩了两个 Godot 的坑（`scripts/car.gd` 的 `_apply_inertia_scale()`）：

- `RigidBody2D.inertia` 属性在**自动模式下恒为 0** —— 那是「自动」这个状态的哨兵值，
  不是算出来的惯量。要读真实值必须用
  `PhysicsServer2D.body_get_param(rid, BODY_PARAM_INERTIA)`。
- 物理服务器要等到**第 2 个物理帧**才把碰撞形状换算成惯量，在那之前读回来是 0。
  所以 `_apply_inertia_scale()` 是异步的，轮询到非 0 再写回去。**如果直接在
  `_ready()` 里同步读，会读到 0、乘完还是 0，倍率静默失效** —— 看上去一切正常，
  实际什么都没改（第一版就是这么写的，×0.5 到 ×5.0 结果完全一样才发现）。

代价是前两个物理帧车身仍用自动惯量，33 毫秒，感觉不到。诊断脚本留在
`tests/inertia_probe.tscn`。

地形手感改 `scripts/terrain.gd` 顶部常量：`BASE_AMPLITUDE`（初始起伏）、
`MAX_AMPLITUDE`（最陡上限）、`AMPLITUDE_PER_1000`（变陡速度）、`_noise.frequency`（山丘疏密）。

云在 `scripts/background.gd`。它有个和其他图层不一样的地方：**横向有视差
（0.18），纵向没有**。三层远山是横竖都按自己的系数滚动，但云如果也照做，摄像机
一升高云就会沉到山脊线以下，穿帮。所以云的纵向基准是直接锁死在最远那层山的
基准线上方的（`FAR_LAYER_BASE_Y - CLOUD_RISE`），随便摄像机在哪都待在天空里。

每朵云由 5 个实心白圆 + 1 个扁矩形（平底）拼成，位置和大小用确定性哈希
`_hash01()` 按序号生成，所以同一个位置永远是同一朵云，不会随摄像机抖动。
圆的 alpha 是 1.0 而不是半透明 —— 半透明的圆叠在一起，重叠处会比别处更白，
接缝一眼就能看出来（`tests/probe_clouds.tscn` 的 ASCII 图里看得很清楚）。

车壳的离地间隙也很关键：`scenes/car.tscn` 里 `Chassis` 的碰撞多边形底面如果离轮底太近，
车会横架在 V 形山谷上搁浅（轮子悬空、被静摩擦锁住，再也出不来）。当前留了约 31px。

### 隧道上壁的厚度（`scripts/tunnel.gd` 的 `ROOF_MIN` / `ROOF_CROWN`）

要求是「石头要盖得住屏幕上半部分」。**这不是一个能随手调的观感参数**，它是从镜头
位置反推出来的 —— 因为**车手头顶碰到洞顶就是死**（见「洞顶是死亡区」那条），
车身最高只到「洞顶下沿 + 头顶高度」，而镜头挂在车身上方 `HillGame.CAMERA_LIFT`，
于是：

```
厚度 ≥ (CAMERA_LIFT − 头顶高出车身) + 半个画布高 ÷ ZOOM_FAR
```

实测那一项是 `90 − 77 = 13` 像素。画布高取 `stretch/aspect = expand` 能出到的最高一档
（4:3 平板 = 960），要求就是 `13 + 480 ÷ 0.62 ≈ 787`。**改镜头、改车高（`CAR_HEIGHT`
或车手节点的位置）、改 `ZOOM_FAR`，这个数就得重算** —— `tests/features.tscn` 的
隧道第 ⑨ 节会把这三档画布各算一遍，再从**画出来的多边形**上量最薄处核对，
对不上就红。所以不要去动它，让它自己钉住。

### 车灯（`scripts/night.gd`）

**只有黑夜图有车灯**（`Maps.is_night()`）：别的图压根没有挡布，开了只有油耗、没有光。
开关是空格 / 手柄 B，或者点 HUD 上那一格（手机上那一格是唯一的开关），两条路都走
`HillCar.toggle_headlights()` 这**一个**入口 —— 各写一份的话，按钮那边迟早忘了同步
状态，表现是「按钮亮着、路上没光」。

夜里**唯一的光就是车灯**。关着的时候全屏只剩 `UNLIT_LIGHT = 0.05` 那条地板（用户原话
「未被车灯照到的地方亮度改为白天的 0.05」，于是挡布从纯黑变成 α 0.95 的黑，远处还剩
一层轮廓），**连车自己都只剩 5%** —— 那是用户看过第一版之后补的「只有车灯才有灯光，
车周围还是暗的」（第一版在车周围留了个永远透亮的「洞」，已经删掉了）。
开灯之后屏幕上的亮度是几个来源里最亮的那个，黑度是它的补数（`HillNight.screen_alpha()`）：

- **光池**（`car_light()`）：车壳被自己的灯照亮一点 —— 用户从「完全黑掉」和「被自己
  的灯照亮一点」里选了后者，翻车、翘头时才看得清姿态。峰值 `CAR_PEAK` 0.40，比锥形
  暗得多；芯 `CAR_CORE` 120 px 满亮（**红线：芯得整个装下车**，`tests/shapes` 现量每台
  车轴心到最远一角），往外 `CAR_SOFT` 90 px 淡没；
- **车灯锥**（`cone_light()`）：`CONE_HALF_DEG` 22° 半角 / `CONE_SOFT_DEG` 9° 糊边 /
  `CONE_REACH` 820 px 照程（10 px = 1 m，就是用户要的「灯光长度有限」）。照程是硬限，
  而且**光强随距离衰减** —— 用户后来补的「光线的强度随距离衰减」：`CONE_NEAR` 120 px
  以内满亮（接上光池的外沿），之后 smoothstep 一路暗到照程尽头正好为 0，半程约剩五成。
  上一版是「前三分之二满亮、最后一截才糊」的平顶带，看着像贴在路上一张亮纸。
  **锥尖在车头那颗灯珠上，不在车轴心** —— 从轴心射的话，车壳自己的前半截
  会落在锥形里，被一条 44° 的亮楔子切成「前亮后暗」两截。

车头那两颗灯珠是**画出来**的（用户原话「需要把车灯画出来」）：开着时两颗暖白灯珠带
一圈散光；关着时**不画** —— 整辆车都在 95% 的暗里，单画两个灯碗会变成两个悬空的
黑点。摆法是从车壳的碰撞多边形上**现量**的（`HillCar.headlight_lamps()`：前端、离底边
45% 和 20% 车高，先远后近），不是写死的偏移 —— 八辆车的车头天差地别（摩托是个尖、
大巴是一面墙、赛车是个铲），写死的偏移在半数车上会把灯画到车壳外面去。`tests/shapes`
逐台车验两颗灯都落在车壳多边形里、灯珠大到看得见。

三个不显然的实现点：

- **整块挡布是一张不重叠的网**。角度按两段给：车灯那 44° 单独细分 18 份（不细分
  的话整圈那 32 份在这 44° 里只放得下四份，车灯会被画成一个三角形），其余整圈粗分
  32 份，两段合起来正好一整圈。**重叠不行**：两块 α 0.95 叠起来是 1 − 0.05² =
  0.9975，在 95% 的黑里是一条看得见的深色缝。`tests/shapes` 拿角度之和 = 360° 和
  「半径一圈圈变大」把这条钉住了。
- **扇形从半径 0 开始铺**，不是从池芯开始：池芯不透明（灯开着时那儿 α = 1 − 0.40），
  从 `CAR_CORE` 才铺的话车周围会留一块根本没涂过的画布 —— 屏幕上就是「车所在的那块
  还是白天」。关灯时整块挡布只有 0 和 `REACH` 两圈（一个颜色，32 片足够）。
- **锥形那条衰减是靠半径方向的圈数画出来的**（`CONE_RINGS` 7 圈，117 px 一段，
  段内只有线性插值 —— 颜色是逐顶点算的，圈和圈之间 GPU 不会替你补曲率）。
  上一版锥形是平顶带，圈多圈少都看不出来；现在整条都在往下掉，退回 5 圈的话
  半程那一段就会插出折角。
- **开灯费油是固定的额外一项**（`HillCar.HEADLIGHT_DRAIN` = 2.2/s），加在悬停倍率
  **之后** —— 加在之前的话，登月车悬停时开灯会跟着翻三倍。用户原话是「耗油速度是
  前进速度的 0.5 倍」，**没有照字面做**：车速表上的数是 m/s 换算的 km/h，字面乘
  0.5 会让满油一秒见底。改成「油门耗油（4.4）的一半」，满油开灯约 15 秒
  （不开灯空转 62 秒、全油门 23 秒）。这个数照样乘本图的 `fuel_scale`。

那个 0.5 的换算在测试里**只量意图**（「比空转费、比全油门省」），不钉死比例：
`fuel_idle_drain` / `fuel_throttle_drain` 是 `@export`，车主会在编辑器里试着调，
钉死一半只会让正常的调参变成一片红。

### 屋顶图的烟囱（`scripts/chimneys.gd` + `scripts/rooftop_art.gd`）

屋顶图是**形状地图**：地表不是噪声，是一栋栋 800 像素宽的房子（`HillTerrain.roof_profile`），
每栋分成「落点 / 钢梯 / 中间平屋面 / … / 跳台」。烟囱就长在**中间那几级平屋面**上，
把它往上托一把。

**一半是画，一半是力，两边共用同一个矩形**：

- **砖柱子**由画师画（`HillRooftopArt._draw_chimneys()`：砖色底 + 每 `BRICK_COURSE`
  一条砖缝 + 顶上一圈压顶 + 黑色的囱口）；
- **力**和**烟**由 `HillChimneys` 摆（一个 `Area2D` 力区 + 一堆上升的烟团）。

两边都从 `HillChimneys.chimney_rect()` 拿位置（剖面 + `Maps.chimney_at()` 的骰子 →
世界坐标）。各算一遍的话，改一次骰子就会出现「囱口在左边、烟从右边冒出来」。

**力度是「几倍自重」，不是写死的牛顿数**：`SMOKE_LIFT_G = 1.4` → 净 **+0.4 g**（开过去
被托得离一下地，但绝不会自己飞起来；那一档要 1.9）。运行时用车自己的总质量
（`HillCar.total_mass()`）**和本地重力**（`HillCar.local_gravity()`）现算 —— 车主在编辑器里
改 `car.gd` 的质量、或者月球那种 0.35 重力的图上，这条都跟着对。力只加在**车壳**上：
车是三个刚体，`Area2D` 会把三个都报上来，逐个加是设计值的三倍，而且车壳和轮子分别受力
还会多出一个扭矩把车掀翻（沙尘暴那边同一条）。

**力区的底边压在屋面上，不是压在囱口上。** 车是**沿着屋面开过去**的，它的车壳正好在
屋面往上 90 像素那一带，而囱口（屋面往上 46～78）只在当中一小截 —— 底边放在囱口的话，
只有腾空跃过屋顶时才吃得到力，那正是「开过去被托一把」的反面。所以烟团从囱口往上飘，
力却从屋面就开始算；这一段差在画面里看不出来（烟半透明、力区根本不画），手感却是两回事。

**烟囱不挖地形、不摆刚体、不挡路**：它不改变地表一像素（`FEATURE_CHIMNEYS` 那一行的
`depth` / `edge` 都是 0），力区是 `collision_layer = 0` 的 `Area2D`（只**看** 1 层的车），
车撞上去直接开过去。摆不下的房子（骰子没中、或者中间那几级平屋面都太窄）**连 Area2D
都不建**。摆位跳过第 0 级（落点）和最后一级（跳台）：落点是车砸下来的地方、跳台是唯一
能把速度捡回来的地方，在这两处放一柱向上的烟等于白送一个 buff，而缝宽是按没有烟的时候
标定的。

两处容易踩的：

- **烟画在车后面**（本节点和地表同层 `z = 0`，车在 `z = 1`）：半透明的灰盖在车上会把车
  糊住，而车是玩家唯一要盯着的东西。
- **屋顶图的画师必须挂在土色之后**（`terrain.gd` 的 `_build_chunk`：「先建、后挂」）。
  同一层 `z`，后画的在上面 —— 挂反了的话那块实心地块会把整面立面连窗户一起埋掉，
  只剩探出屋面那几笔瓦尖。**这个错误测试全绿**（车照样开得动），只有截图看得出来，
  所以 `tests/shapes.tscn` 里专门钉了一条「画师排在土色之后」。

### 屋顶图的窗户（`scripts/rooftop_art.gd` 的 `window_lit` / `window_tick`）

窗户的亮暗是**活的**（用户要的「窗户动画」），但**只认整拍，不认帧**：`WINK_STEP = 1.0`
秒一拍，`tick = floor(t / WINK_STEP)`，再拿 `(种子, 区块号, 层, 列, tick)` 哈希出亮暗。
一扇窗的周期是 12～60 拍（`ACT_MIN` / `ACT_MAX`），**每扇各掷各的相位** —— 同一个周期的
话到点了整条街一起眨眼，一眼就看出来是假的。

时钟用的是**绝对时间**（`Time.get_ticks_msec()`），不是自己累加的 delta：区块会随镜头
滚出视野再重建，累加的话重建回来的那栋房子会从自己的第 0 拍重新开始，同一栋房子两次
经过时亮着的窗户不一样。节点只在**拍子翻面**时 `queue_redraw()`—— 一屏三栋房子，
没必要每帧把那几百扇窗重铺一遍。

**「算式在动」和「画面在动」是两回事**：`tests/shapes.gd` 能证明 `window_lit` 随 tick 翻脸，
但无头跑不发 `NOTIFICATION_DRAW`，它证明不了这脸画到了屏幕上 —— 用户报的正是这一种
（拍子在翻、窗户一辈子一个样）。所以另有一个要窗口的 `tests/shot_roof_wink.tscn`：同一栋
房子、同一个镜头隔十四拍拍两张，**逐像素**比，要求有一批像素在亮窗色和暗窗色之间翻面、
**且其它像素一个都没变**（场上没车没尘土，镜头钉死，除了窗户没有东西该动）。

## 手机版

导出一个能装的安卓包，并给触屏补上一套操作和一套版面。

```bash
GODOT="D:/Downloads/Godot_v4.7.2-stable_win64.exe/Godot_v4.7.2-stable_win64.exe"
"$GODOT" --headless --path . --export-debug "Android" ./HillClimbRacing.apk
```

（`Android` 是 `export_presets.cfg` 里 [preset.1] 的名字。第一次导出前要在编辑器
设置里填好 `export/android/android_sdk_path` 和 `java_sdk_path`。）

### 操作层（`scripts/touch_controls.gd`）

**车那边一行都没改。** 踏板喂的就是 `drive_forward` / `drive_back` 两个动作 ——
和键盘走同一套。这么做有三个好处：登月车的「双键悬停」白捡（它本来就是
「两个动作同时按下」）、键盘和触屏的行为不会各飘各的、`car.gd` 不需要知道
自己是不是被手指开着的。

几处不显然的地方：

- **`Input.action_press` 是全局状态。** 按键松开事件丢了就是丢了，动作不会自己
  复位 —— 而它挂在 `Input` 单例上，跨场景也不清。所以「把动作放开」有**四个**
  必须做的时机：车翻了（`set_locked`）、整层关掉（`set_enabled(false)`）、
  退出场景（`_exit_tree`，顺便把 `get_tree().paused` 复位）、切到后台
  （`NOTIFICATION_APPLICATION_FOCUS_OUT`，来电或 Home 键之后指头再也不会发
  抬起事件了）。漏掉「退出场景」那一条，表现就是**下一局一开局车自己窜出去**，
  而且没有任何输入能让它停下来。`tests/mobile` 的 D 段把这四处逐条钉住了。
- **多指靠 `_hold` 计数。** 两根手指踩同一个踏板时，只有第一根去按动作；两根
  都记在账上。不记账的话先抬起的那根会把另一根踩着的那一脚也放掉。
- **拖动只在踏板之间换区。** 暂停键和菜单按钮是「点一下」语义：按下暂停的那根
  手指只要稍微挪一下，就会被判成点了「重开」，那样根本没法用。
- **可见性不等于开关。** `Node._input` 和 `visible` 无关（`visible` 只管 GUI 的
  命中测试），所以整层另有一个 `enabled` 布尔。桌面版照样把这层建出来，只是
  `enabled=false`，行为和加它之前逐位相同。
- 暂停键的顶边 `PAUSE_BTN_Y = 74` 是**卡着右上角那行地图名算的**
  （`HillHud.MAP_NAME_BASELINE` + 字体下缘 = 59）。`tests/mobile` 拿真字体量出
  这个下缘再比，不是凭「大概不会撞上」。

### 两套版面

`HillHud.setup()` 多了一个 `touch` 参数。桌面版面的坐标**一个数都没动**，
`tests/mobile` 的 E 段专门断言了这一点。

手机上三个角要让给踏板和暂停键，于是：

| 东西 | 桌面 | 手机 |
| --- | --- | --- |
| 油条 | 左下角 (30, 高-60) | 底部正中（两个踏板之间那条缝） |
| 车灯那格 | 右上角，和地图名对齐右边 | 并排贴在油条左边，中间留 12 px |
| 道具栏 | 右下角 | 上抬 120 px 并水平居中 |
| 仪表盘 | 离底 24 px | 离底 `HillTouchControls.bottom_inset() + 12` = 240 px |
| 结算面板 | 只有键盘提示 | 2×2 四个按钮（再跑一局 / 换车 / 换地图 / 回车库） |

仪表盘那个数**是从踏板那边推出来的，不在两个文件里各写一遍** —— 踏板改大改小，
表盘跟着动，不会出现「踏板长大了、表盘还留在原地被压住」。同理，HUD 把
`fuel_rect()` / `items_rect()` / `dashboard_cluster()` / `headlight_rect()` 都开成了
纯函数，画的、命中测试的、测试里比对的读的是同一份，于是「两套版面不许打架」是一条
**能断言的**性质（三个画布尺寸 × 七个矩形两两比对），而不是一句注释。

车灯那格**只有黑夜图上有**（`headlight_rect()` 返回零矩形，于是不画、也点不着），
手机上那一格是**唯一的**车灯开关 —— 没有键盘可按。它和油条是并排的一行，
坐标是**从 `fuel_rect()` 推出来的**，油条挪了它跟着挪。

### 中文文案在安卓上（`scripts/ui_fonts.gd`）

**手机上「文字全为英文」不是翻译漏了,是字体没找到。**

Godot 内置的默认字体只带拉丁字形（`ThemeDB.fallback_font` 对「中」的 `has_char()` 是
**false**，`tests/fonts` 把这条也钉住了），所以直接写中文会渲染成方块。最早的候选表
**全是桌面路径**（`C:/Windows/Fonts/msyh.ttc`、`/usr/share/fonts/...`、PingFang），
安卓上一条都不存在 —— 于是 `load_cjk_font()` 返回 null，每一屏的 `_cjk` 就是 false，
`_t(zh, en)` 全程返回英文那一份。所有界面文案都是这么写的（`_t()` 的英文分支本来是
给「字体缺失」兜底的，结果在手机上成了常态）。

现在分两段找，**顺序就是优先级**：

1. **问系统要**（`SystemFont` + 家族名列表，`allow_system_fallback = true`）。这是跨平台
   的正路：安卓上它查的是系统字体库，比硬编码路径可靠，也不用把几十兆字体塞进包里。
   名单里 `Droid Sans Fallback` 是老安卓上唯一带汉字的那个，`Noto Sans CJK SC` 是现在
   的通名。
2. 挑不出来才逐个试文件路径（`CJK_CANDIDATES`，安卓那几条是给「不认家族名的老机器」
   兜底的）。

两段都过一道 `has_cjk()`：**拿真字形验一次**。只看 `load_dynamic_font()` 返回 OK 是
不够的 —— 那个字体可能一个汉字都没有，画出来是**豆腐块**，比退回英文还难看，而且更
难查（看着像编码问题）。

**包里一个字体文件都没有**（`unzip -l HillClimbRacing.apk | grep -i ttf` 是空的，
`CJK_CANDIDATES` 命中的全是系统路径），所以安卓上中文是**完全**押在系统字体那一半上
的，没有任何兜底。真机上万一出豆腐块，唯一的补救是往 `CJK_CANDIDATES` 之外再塞一个
字体进包（几十兆，换来的是确定性）。

`tests/fonts.tscn` 怎么测的，和为什么在无头环境里也能测：

- 断言**本机真的能找到一个带汉字字体的文件**（这台机器上是 `C:/Windows/Fonts/msyh.ttc`，
  直接用 `FileAccess` 扫一遍候选表，和 `file_cjk_font()` 的结论对照），再断言它含界面
  里用到的所有字。
- **不假设系统名能不能对上**：`SystemFont` 那段测的是「名单里有没有中文家族名」「兜底
  开着没有」，换一台没装字体的机器也是这几条。
- **结构检查**（自己维护自己）：除了 `ui_fonts.gd`，任何 `.gd` 都不许出现 `.ttc`/`.ttf`/
  `.otf`（字体路径表只有一份），任何有 `_cjk` 的文件都必须有 `func _t(zh, en)`。加一屏
  忘了接字体，这条会红。

### `project.godot` 里为手机改的

```ini
[display]
window/handheld/orientation=4          # SCREEN_SENSOR_LANDSCAPE，横屏
window/energy_saving/keep_screen_on=true
[rendering]
renderer/rendering_method.mobile="gl_compatibility"
textures/vram_compression/import_etc2_astc=true   # 不加这条导出会被直接拒绝
```

`stretch/mode=canvas_items` + `aspect=expand` 没改：所有版面都是从 `size` 现算的，
真机上事件也会先被引擎换算成画布坐标再送到 `_input`，所以量 `Control.size` 就是
量画布。**画布高度最少是 720**（比 16:9 更宽的手机保持 720、两侧多出来），
窄一些的平板会更高。

### 几点没做的

- **包是 debug 签名的**（`CN=Godot`，Godot 自带的调试密钥）。要上架得自己生成
  一份 release keystore 填进 `keystore/*` —— 那需要编一个密码并明文写进
  `export_presets.cfg`，所以留给你决定。
- `package/unique_name` 是占位的 `com.example.hillclimbracing`，上架前改成
  自己的域名倒写。
- **没在真机/模拟器上跑过**：这台机器上 `adb devices` 和 `emulator -list-avds`
  都是空的（2026-10 查过一次，仍然是空的）。`tests/mobile` 用合成触摸事件把
  「踏板 → 动作 → 车真的往前开」这条路走通了（含一次端到端：按住油门 3 秒车前进
  1491 px），但触屏手感、性能这些只有真机说了算。
- **中文那一段的安卓分支同样没法在这台机器上验证**（上一节）。能验的是「本机
  `file_cjk_font()` 真找得到字体、那个字体真有界面用到的每个字、`_t()` 的接线没漏」；
  **验不了的是「安卓上 `SystemFont` 到底挑不挑得出来」** —— 那段代码的正确性目前只有
  家族名和 `allow_system_fallback` 这两条静态断言撑着。真机上装一次看选图页是不是
  中文，是唯一能确认的办法；万一是豆腐块，说明得关掉 `allow_system_fallback` 或者
  往包里塞一个字体。

- `save.tscn` / `persist.tscn` 见上面「存档」一节。
- `upgrade_calib.tscn` 是改装数值的**实测**校准，分六段：A 静态表（顺带断言
  `Upgrades` 里为了显示推重比而复制的那份车体常量和真车一致 —— 车改了这里没改
  就会静默显示错数字）、B 平路翘头余量、C 40° 稳态爬坡、D 敏捷等级的真实地形
  里程、E1 平地精确烧干用时、E2 真实地形一箱油。跑一次约 4 分钟，因为 E1/E2
  要真的把油烧完，而物理测试不能加速（坑 #1）。
- `garage.tscn` 测购买逻辑、选中环绕、点击命中，以及**版面几何**：拿真实字体
  量出每段文字宽度，断言名称/说明/效果/价格药丸互不重叠。它故意**不把车库挂进
  场景树**，而是手工给 `size` 赋值再调布局函数 —— 因为无头视口是 1280×1280
  （坑 #7），挂进树里量出来的版面是错的。
- `mapselect.tscn` / `vehicleselect.tscn` 里量版面的那几节也不挂进树（理由同上），
  但读存档的那一节（开局光标停在哪）必须挂 —— 不挂进树 `_ready()` 永远不会跑。
  `mapselect` 另外测轮播：窗口外的卡给的是**空矩形**，而空矩形的 `has_point()` 恒为假，
  所以「看不见的卡点不到」是几何上自然成立的，不用另写判断。两页都拿真字体量出
  **每一行文字的墨迹**范围，断言锁卡底板不会把任何一行字**从当中切开**（整个盖住或
  整个露出来都行，切一刀不行）。
  **不点通了的卡**：点第二下会走 `_pick()` → `change_scene_to_file()`，把测试场景本身
  换掉，测试当场就没了。所以这一节只点锁着的卡（买不起就什么也不发生，买下了也只是
  在原地解锁），换图和存档那一步交给 `unlock` / `save`。
- `unlock.tscn` 测解锁经济，**包括真的写盘再读回来** —— 「买完了下次开机还在不在」正是
  要测的东西，用 mock 就测不到了。所以它跑之前把 `user://save.cfg` **整份按字节备份**、
  跑完还原（不是按字段备份：`save_data()` 是整份覆盖写盘，将来存档多一个字段，按字段
  备份的写法就会漏掉它，而漏掉的后果是「跑一次测试把玩家的进度冲掉」）。老档那一段是
  手写一份**没有 `[unlocked]` 段**的 cfg，验证「玩过的就算已解锁」，以及免费的那几张
  **不会**被顺手写进 `[unlocked]`。
- `fonts.tscn` 见上面「手机版」一节。
- `shot.tscn` 在五个时间点截图，最后一张强制把油耗尽，用来检查结算面板。
- `probe_clouds.tscn` 把截图的天空区域打成 ASCII 地图（空白=天空、`#`=云、`o`=山），
  再对结算面板截图做亮度图和按颜色分行定位。

### 测试上的坑

1. **`Engine.time_scale` 不能用来加速物理测试。** Godot 是把 `_physics_process` 的
   delta 直接乘上 time_scale，而不是多跑几个固定步长 —— 实测 `time_scale=8` 时步长从
   0.0167s 变成 0.1314s。那是另一套数值精度完全不同的物理，测出来的「弹跳、卡死、
   里程翻倍」都不代表真实游戏。所有物理测试必须 `time_scale = 1`，代价是一个 45 秒
   的用例就要真跑 45 秒。
2. 步长正确是**可复现的必要条件，不是充分条件**。用粗步长会出现假的不确定性
   （同参数跑出 147/186/694 m 三种结果），所以先怀疑步长；但步长对了以后仍然
   可能有别的东西在飘 —— 见坑 #9。判断方法：**同一份代码连跑两次对拍**，别只看
   一次的数字就往下推。实测分得清哪些段是可信的：
   `upgrade_calib` 的 A/B/E1 三次运行**逐位相同**（E1 都是 16.70s / 26.70s /
   8255 px），C 在 ±2% 内浮动，而 D/E2 修正前能差 1.7% / 37%。
3. **测试会写玩家存档。** 任何实例化 `main.tscn` 的用例都得先 `SaveData.persist = false`。
4. **`inertia_scale` 必须在 `add_child()` 之前设。** `car.gd` 是在 `_ready()` 里
   异步应用它的，进树之后再改不会有任何效果。
5. **场景加载失败时 Godot 会挂住不退出**，输出还是空的，看起来像死循环。这时候去翻
   `%APPDATA%/Godot/app_userdata/HillClimbRacing/logs/godot.log`，八成是一句
   parse error。顺带：`TaskStop` 杀掉 shell 并不会杀掉 Godot 子进程，得 `taskkill //F //IM`。
6. **截图要等够帧。** 把 `car.fuel` 设成 0 之后，车要到**下一个物理帧**才在 `_burn_fuel`
   里判定死亡，HUD 的 `queue_redraw()` 还要再等一帧才真正画出来。直接
   `await RenderingServer.frame_post_draw` 拿到的是结算面板出现**之前**的那一帧
   （这也是为什么有一次像素探测报告「只有金色有文字」—— 它量到的其实是地形和云）。
   现在等 3 个物理帧 + 2 个处理帧。
7. **无头模式下视口是 1280×1280，不是 720。** 所以无头跑 `hud_rect.tscn` 量出来的
   HUD 尺寸和面板基线全是错的（会得到 550/640/700/760/820 这种值）。要量 HUD 几何
   必须开窗口跑；`shot.tscn` 里顺手会打印一次实测值（1280×720 下是
   270/360/420/480/540），可以用它交叉验证。
8. `var ok := got == want` 编译不过 —— 两个 `Variant` 比较推不出类型，得写
   `var ok: bool = got == want`。**同一类错误会反复出现**：从 `Dictionary`
   取值也一样（`var nm := track["zh"]` 报 `Cannot infer the type of "nm"`），
   得写 `var nm: String = track["zh"]`。
9. **装饰性动画不要动碰撞体。** `pickup.gd` 里的金币/油桶有个上下浮动的小动画，
   最早是直接 `position.y = _base_y + sin(_phase) * 4.0`，而 `_phase` 又用
   `randf()` 起头、按**可变空闲帧 delta** 累加。结果这个纯装饰的动画把 `Area2D`
   的碰撞体一起带着动，于是「这一帧能不能捡到」取决于空闲帧的节奏 ——
   同一个世界种子、同一份代码跑两次，真实地形里程能差 **37%**（1459 m vs
   1994 m，42.3s vs 58.8s）：漏捡一个油桶就改变了烧干时刻。
   现在相位由收集物自己的位置播种（种子来自地形 `world_seed`，所以「同种子 =
   同一局」成立），浮动改成**只在 `_draw()` 里偏移画出来的东西**，碰撞体固定在
   原地。凡是「物理世界里的东西」被「按帧率推进的动画」推着动，就要怀疑这一条。
10. **`queue_free()` 是延迟到帧末执行的。** 测完一段地形换下一段时，不等一帧的话
   新旧碰撞体会重叠一帧，新出生的车正好卡在旧碰撞体内部被弹飞。
   `upgrade_calib.gd` 的 `_clear_world()` 就是干这个的：`queue_free()` 之后
   `await get_tree().process_frame`。这个坑在 D 段和 E2 段各踩了一次 ——
   两次的表现都是「所有配置一律 0 m 秒翻车」，很像是物理参数写错了，
   其实只是上一段的地形还压在这一段的出生点上。
11. **`get_colliding_bodies()` 要先开 `contact_monitor`。** 不开的话它恒返回空数组
   并报 `Parameter "contact_monitor" is null`，于是「前轮离地时间」会恒等于总时长，
   看起来像车一直在飞。要同时设 `contact_monitor = true` 和
   `max_contacts_reported`（用 8 就够）。
12. **新加 `class_name` 之后必须跑一次 `--import`。** 全局类缓存没刷新的话，
   所有引用它的脚本都会报 `Identifier "Upgrades" not declared in the current scope`，
   而且 Godot 是**挂住不退出**的（坑 #5），表现为一次几百秒的假死。
   先 `--import`（会打印 `update_scripts_classes | Upgrades`）再跑测试。
13. **合成触摸事件要 `push_input(ev, true)`，第二个参数不能省。** 传 false（默认）
   时引擎会拿 `final_transform` 的逆把屏幕坐标映射回画布坐标 —— 那是真机上
   「手指位置 → 画布位置」那一步，引擎自己的活。可无头模式下根本没有真窗口：
   `window.size` 是 **64×64**、`final_transform` 缩到 0.05、视口是 1280×1280
   （坑 #7 的另一面），于是 (1166, 606) 被映射成 (23320, 12120)，一个踏板都命中
   不了。传 true 表示「事件已经是画布坐标了」，正是真机上变换完之后 `_input`
   实际收到的东西 —— 测试里那些矩形也都是画布坐标，两边同一套。
   症状很有欺骗性：`zone_at()` 一直返回 `""`，看起来像操作层的命中测试写错了。
